# IR 전수 투어 — 스토리보드 (4분 00초)

`scenarios/ir-full-tour.json` 의 설계 의도. 27장면(카드 8 + 화면 19), 6개 역할.

짧은 요약본(`signup-to-trace`)이 "되긴 되는구나"를 보여준다면, 이 버전은 **"여섯 주체가
같은 기록을 공유한다"**는 구조 자체가 제품이라는 것을 보여주는 것이 목적이다. 그래서
역할 전환이 연출이 아니라 실제 계정 전환으로 일어난다.

## 연출 판단

**역할 순서를 소비자부터 잡은 이유.** 투자자에게 가장 먼저 와닿는 것은 규제 구조가 아니라
"내가 든 제품이 진짜인가"다. 소비자 화면에서 원장을 한 번 보여주고 나면, 이후 네 역할은
모두 *같은 기록의 다른 단면*으로 읽힌다. 반대로 콘솔부터 시작하면 관리 도구처럼 보이고
소비자 화면이 부록이 된다.

**역할 전환을 자막이 아니라 계정 전환으로 한 이유.** "이번엔 관세청 화면입니다"라는 자막은
연출이고, 로그인된 계정이 바뀌면서 상단 밴드 색과 권한이 함께 바뀌는 것은 증거다. 특히
관세청 뷰는 정부 밴드(남색 + 금색 라인)와 **쓰기 권한 없음**이 실제로 다르게 렌더링되는
화면이므로, 이것이 별도 구현이라는 점이 화면 자체로 드러난다.

**60번과 70번이 같은 `/console` 주소인 것이 이 영상의 핵심 한 컷이다.** `docs/login-accounts.html`
의 공식 딥링크에서 GOV_INSPECTOR 의 `next` 는 `/customs` 가 아니라 `/console` 이다. 즉 주소는
같고 권한만 다른데 화면이 통째로 달라진다. 자막 한 줄로 설명할 것을 두 장면 연속 배치로
보여주는 쪽이 훨씬 강하다 — 권한 모델이 UI 분기가 아니라 제품 구조라는 뜻이기 때문이다.

**"아직 안 된 것"을 숨기지 않는다.** 75번 장면은 앵커 상태가 `simulated`라고 화면에
그대로 나오고, 캡션도 그렇게 말한다. 실사에서 한 번 뒤집히면 나머지 전부의 신뢰가
같이 무너지므로, 미구현을 구현된 것처럼 비추는 프레임은 한 장도 넣지 않는다. 같은 이유로
AVP(성인인증) 역시 "요건"으로만 언급하고 벤더 연동 화면은 넣지 않았다 — 현재 구현은
ID 스캔·라이브니스 결과를 **입력으로 받는** 단계까지다.

**관리자 장(70→85)을 UID 의 일생 역순으로 배치했다.** 대시보드로 전체를 본 뒤 생산(발행) →
통관(세율) → 교환(정산) → 원장·앵커(증명) → 감사(보존) 순으로 내려간다. 모듈 목록 순서대로
훑으면 기능 나열이 되지만, 이 순서로 가면 "UID 하나가 어디서 태어나 무엇으로 증명되는가"
라는 하나의 이야기가 된다. 앞선 세 장(소비자·가맹점·단속)에서 본 화면들이 여기서 전부
한 번씩 회수된다.

**생산·통관·정산 장면의 캡션이 전부 '무엇이 불가능한가'를 말한다.** 부분 성공이 없다,
과거 세액이 소급 변동하지 않는다, 두 번째 교환이 정산에 올라올 수 없다 — 투자 심사에서
"할 수 있다"는 주장은 흔하고 검증이 어렵지만, "구조적으로 안 된다"는 주장은 한 번 보면
확인된다. 73번의 "7월 세율을 지금 등록해도 3월 배치는 안 흔들린다"가 그 전형이다.

**캡션이 화면보다 한 박자 먼저 나온다.** 먼저 말하고 그 다음에 보여줘야 시선이 어디로
갈지 안다. 반대 순서면 투자자가 화면을 훑는 동안 캡션이 지나간다.

## 다시 찍을 때

```bash
export LM_DEMO_PASSWORD='...'                      # 저장소에 넣지 말 것
npm run check   -- scenarios/ir-full-tour.json --base-url <배포주소> --check
npm run record  -- scenarios/ir-full-tour.json --base-url <배포주소> --out out/full
npm run produce -- out/full --out out/full/ledgermark-ir-full-tour.mp4
```

한 장면만: `--only 60-customs`. 계정이 바뀐 경우에만 `--refresh-auth`.

`auth.accounts` 의 이메일 6개는 `docs/login-accounts.html` 기준으로 맞춰 두었다
(`consumer` / `store` / `distributor` / `officer` / `inspector` / `admin` @ledgermark.com,
공통 비밀번호). 문서에 따르면 이 계정들은 서버 부팅 시마다 보장되므로 재배포 후에도
유효하다. 계정을 바꾸면 저장된 세션의 지문이 달라져 **자동으로 다시 로그인**하므로,
`--refresh-auth` 를 깜빡해서 이전 계정으로 찍히는 일은 생기지 않는다.

레거시 시드 계정(`admin@ledgermark.test` 등, 비밀번호 `ledgermark1234`)도 아직 살아 있다고
문서에 적혀 있다. IR 종료 후 정리 대상이다.
